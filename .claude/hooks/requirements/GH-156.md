### GH-156
- text: `append-only-docs.sh` reads the command twice, as it came and with its
  backslash line continuations joined by `cs_join`, and refuses when either
  reading is refused. So every spelling it refuses on one line — `rm`, `mv`,
  `cp`, `truncate`, `tee`, `sed` or `perl` with an `-i` option word, and a
  truncating redirect — is refused with a continuation anywhere between the verb
  and the path, or inside the path. A line bash does not continue — an even run
  of backslashes, or one in a comment — is still read unjoined by the first
  reading, so a destroying command on the line after it is refused as it was
  before #156. `>>` behind a continuation stays permitted, and so does a
  revisable directory. Its load guard requires `cs_join` beside
  `cs_tool_input` and `cs_within_cap`.
- from: #156, found by #106's invariance families on the first run of the
  `continuation` transformation against an `append-only-docs.sh` seed, which is a
  seed only because #141 brought the hook into their scope
- kind: defect-permitting
- status: active
- variants: transformation: continuation continuation-inword
- note: the hook matches paths where they stand, with `grep -E`, and `grep`
  matches within a line; the command never passed through `cs_join`, so a
  continuation between the verb and the path hid the path from a rule that
  requires both on one line. Measured: `rm`, `mv`, `cp`, `tee`, `truncate` and
  `>` were all permitted behind one backslash, and so was `sed` with a
  continuation before its `-i`. It was #84's shape again: `no-pr-decisions.sh`
  calls `cs_join` for this exact reason, one file away from the hook that did
  not. Its first version read the joined text alone, and that opened a hole
  of the same class the other way: `cs_join` joins any trailing backslash and
  bash continues only an odd run and never a comment, so `echo done \\`, a
  newline and `rm -f` an entry — refused before — was permitted, the verb glued
  onto the word before it (review of PR #329, round 1). The raw reading is what
  closes that, since it is the hook as it was. What the fix gives up is in the
  refusing direction only. The joined reading gives any command the verdict
  the hook gave before #156 to the same text with each line-ending backslash
  and newline taken out. Where bash joins too, that is the one-line verdict,
  looseness included — a verb read out of prose or an argument, #237's shape.
  Where bash does not — single quotes, a comment, a quoted heredoc's body — a
  destroying verb or a `>` anywhere on a line ending in a backslash, before a
  line naming an entry, is refused: `rm -f tmp.txt  # clean \` over `cat` an
  entry, and `cat >>` an entry from a quoted heredoc with a Markdown hard line
  break after a line mentioning `rm`, which is the append the directory exists
  for. And `docs/dev-log\`, a newline and `book`, which is `docs/dev-logbook` to
  a shell, stays refused by the raw reading. What it does not reach: an `-i`
  bundled into another option, `perl -p\`, a newline and `i`, or `sed -Ei`, is
  permitted as `perl -pi` is on one line, which is #246's; a destroying command
  in a subshell or a substitution is #345's. The `variants` value names the two
  transformations that reach its continuations, between two words and inside
  one. The shapes of the first reading — a non-continuing line in front of a
  command — are not among them: as a transformation they would depart in every
  hook that reads `cs_normalise`'s text, which is #337, and they belong to its
  fix. `checks/GH-156.sh` pins every verdict above that is GH-156's, and not
  the two that are #246's and #345's. Until #156 this entry was
  `gap → #156`, and the families' `docs-truncate + continuation` row asserted
  the permitting verdict; that variant is an ordinary check of the seed's BLOCK
  now.
