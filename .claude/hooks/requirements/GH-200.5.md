### GH-200.5
- text: `split-requirements.sh` moves every `GH-` entry out of `requirements.md`
  into a file of its own, byte for byte, and leaves the rest of the file as it
  was; a second run moves nothing; an entry whose file already holds exactly it is
  no conflict; and it refuses, writing nothing, a file already there holding
  something else, an ID outside the grammar, an ID written twice, whatever the
  suite's reader would refuse in a file it wrote -- a heading that is more than
  its ID, and a line in the entry's block that is neither a field, nor the
  continuation of one, nor blank -- and a `GH-` heading the reader would refuse
  where it stands, under any `##` heading but the three that hold requirements
  or before the first. It says which files it wrote apart from those already
  there with the same bytes. Byte for byte but for one case, pinned: a last line
  with no newline gains one. On the merge that brings the split it compares
  each entry three ways, reading the base and the branch side out of git: an
  entry changed on the branch only is written, with the SPLIT_MOVED token that
  has to move; one changed on the dev side only keeps its file; one changed on
  both is refused; and so is a version in requirements.md the branch never
  committed. Which comparison runs is decided by the state of the repository,
  whatever the directory argument: three ways during a merge, on a last commit
  that is that merge, and with `--base`/`--branch`; refused during a rebase,
  cherry-pick, revert or squash merge, and while requirements.md is unmerged;
  two ways otherwise. Each refusal of a file that differs -- the three-way
  ones, and the two-way conflict -- names a step a second run accepts:
  `--resolved <ID>`, which leaves that file as it is.
- from: #200
- kind: defect-permitting
- status: active
- direction: static: it runs the script against fixtures and reads what it wrote
- note: It is what a pull request open across the split runs once it merges the
  dev branch that carries it, which is why it is a script and not only the
  commit that made the split. That merge is a content conflict on
  requirements.md, the branch's whole `GH-` section against the pointer
  paragraph, and a two-way run could not tell a branch's edit from its stale
  copy of an entry the dev side changed: keeping the dev side lost the edit
  with "nothing to move", and keeping the branch side refused both kinds alike.
  Measured on #158 and #184 by rev-agent-200, round 4 of #210, which is why the
  run during the merge, with no directory, is three-way.
