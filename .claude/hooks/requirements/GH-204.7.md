### GH-204.7
- text: The driver sources the unsplit file first and the end-of-run file last,
  whatever else it sources, through one call of `source_checks`. Once the last
  file has run, the driver compares the sourcing record with what its list
  says it should hold -- every file started and run to its last line, in that
  order, in the driver's shell -- and fails the run when they differ: with a
  row, and again in a verdict taken after every helper has run, by code that
  calls no function and can set the failure and not clear it. And a run that
  ends with status 0 before that, because a file ran `exit 0`, leaves with
  status 1 from its EXIT trap, which asks the same question and says why; any
  other status is kept.
- from: #204
- kind: defect-permitting
- status: active
- direction: static: it drives the verdict and the EXIT trap against fixture
  records and reads the driver's list and its one call
- note: The routine's own questions are asked in whatever shell it runs in, so
  a routine run in a subshell prints its FAILs there, uncounted, and the run
  stays green; only a question asked from the driver's own shell after the
  last file can see that, and only the EXIT trap can see a file that ended the
  run with `exit 0`, which prints no verdict and leaves with the status a
  caller reads as a pass. The end-of-run file is last because it reads the
  record every check before it wrote. Only the two ends of the list are held
  as a literal: an issue file is added between them by the loop that writes
  it, and a literal of the whole list would be a second line every such loop
  edits, beside the list itself, which is the one such line the split leaves.
