### GH-204.1
- text: `checks/library.sh` defines every function the check suite calls from more
  than one of its files, and no other. Each section of `check-hooks.sh` counts
  as a caller of its own, and so does its prelude; a call made inside a function
  counts for every caller of that function; and a function the suite removes
  with `unset -f` is a fixture, not a helper. The suite derives the set from its
  own code and fails on a function it finds on the wrong side of the file
  boundary, in either direction. A definition is any spelling bash takes at the
  left margin: `name()`, `name ()`, `function name` and `function name()`. It
  also fails on a name defined more than once, in one file or across the
  suite's files, and on a name the suite defines that the tokeniser it sources
  into the same shell also defines, because bash keeps whichever definition it
  read last and says nothing about the other.
- from: #204
- kind: defect-permitting
- status: active
- direction: static: it reads the suite's own code, not a verdict on a command
- note: The defect this stands against has happened here once already. A helper
  defined in the section that first wanted it, and called from a section that
  runs earlier, runs as `command not found`, which prints no FAIL and sets no
  FAILED: the tokeniser-header audit ran twelve such calls to `present` with the
  suite green, before the audit was moved below the helper. Once checks live in
  files of their own, a helper left in one of them is that defect waiting for
  the file order to change. The derivation reads code, not text: quoted strings,
  comments and heredoc bodies are blanked first, so a name in a label is not a
  call. What it does not see, named: a call made through a variable,
  `"$helper" args`, is counted only where the name itself is written as a bare
  word, which is how `drive_helper` is handed its helpers today; a function
  defined indented, inside another function or an `if`, is read as part of the
  code around it; and a `case` arm's `)` inside a `$( )` closes it early for the
  scanner. A file the scanner does not finish in plain code is reported and
  fails the check, so that last one cannot pass silently. An indented
  definition is not counted as a second one either, so a helper redefined
  inside a function or an `if` is not reported; nor is a name bash takes and
  an identifier does not spell, such as `function a-b`. The `function` and
  `name ()` spellings were read by nothing until review of PR #216 (round 2)
  inserted `function holds { ... }` and `holds () { ... }` above the #204 section
  and the run stayed green. GH-204.5 now fails the run on a call that finds
  no command, which catches the misplacement after the fact; this still asks
  it first, because it names the function and where it belongs.
