### GH-204.5
- text: A command the suite calls and bash cannot find fails the run, wherever
  it is called: in the suite's own shell, in a subshell, inside a `$( )`, or
  inside a function. The suite writes each one down as the line bash itself
  prints, `<file>: line <n>: <command>: command not found`, with the file and
  line that called it; prints that same line on stderr and nothing into a
  value a `$( )` captures; and fails at its foot on anything written down.
- from: #204
- kind: defect-permitting
- status: active
- direction: static: it drives the suite's own handler and reads what the run
  wrote down
- note: A helper missing from `checks/library.sh` runs as `command not found`,
  which prints no FAIL and sets no FAILED. The load guard asks for the five
  functions every check prints through, and nothing asked about the other forty:
  with `lacks` deleted the run printed 35 such lines on stderr and ALL CHECKS
  PASSED. Found by review of PR #216. Bash runs `command_not_found_handle` in an
  environment of its own, so the handler cannot fail the run itself; it writes
  to a file, and the foot of the suite reads it. What it does not see, named: a
  command missing in the `--matrix` program, which runs after the foot; one
  missing before the fixtures directory exists, which prints and is not
  counted; and one missing in a child the suite runs with `bash -c`, which is
  another shell and does not inherit the handler. Exporting it would reach
  those children, and the hooks the suite runs are such children, whose own
  stderr it would change. Round 2 of the review found the file and line
  claimed and not asserted, and the message said to be bash's when it was
  not. The record is asserted against literals, and stderr against what a
  child `bash`, which does not inherit the handler, prints for the same file:
  round 3 found the stderr check written in the handler's own format, so it
  could not have seen a bash whose message differed.
