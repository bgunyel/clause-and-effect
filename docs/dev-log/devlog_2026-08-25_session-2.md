## The panelist is not one server, and nothing recorded which one it was

**This is the session's finding and everything else follows from it.**

OpenRouter routes one model id to whichever upstream provider it picks. The
providers differ in what they can actually do, they change from call to call,
and until this session the eval had no record of which one answered.

The evidence was assembled from three free sources: the generation ids recorded
by the previous session's item-3 plumbing, looked up on
`/api/v1/generation`; OpenRouter's per-model endpoint listing; and — supplied by
Bertan from the OpenRouter web console — the rows for the 2026-08-23 runs, whose
reports predate generation ids entirely.

### MiniMax's channel assignment was decided by a rate limiter

| run | MiniMax score | provider |
|---|---|---|
| 2026-08-23 `162138`, function_calling | **6/6** | **Venice** ×6, all `tool_calls` |
| 2026-08-23 `165801`, function_calling | **2/6** | **Parasail** ×5, Venice ×1 |
| 2026-08-23 `181319`, json_schema | **6/6** | **CoreWeave** ×6 |
| 2026-08-25 reasoning-channel | **0/2**, both channels | **Parasail** ×4 |

**The console rows were matched to the runs by cost, not by timestamp alone.**
Venice ×6 sums to **$0.008409** against report `162138`'s recorded $0.008409 for
MiniMax; CoreWeave ×6 to **$0.002413** against `181319`'s $0.002412. Both match
to the last displayed digit, which is what makes the provider attribution
evidence rather than inference. That method should not be needed again, and the
design document exists so that it is not.

OpenRouter's own endpoint listing explains every row (**measured**,
`/api/v1/models/minimax/minimax-m3/endpoints`):

| provider | `tools` | `response_format` | `structured_outputs` |
|---|---|---|---|
| Venice | ✅ | ❌ | ❌ |
| CoreWeave | ❌ | ✅ | ✅ |
| Parasail | ✅ | ✅ | ✅ |

Every MiniMax success came from Venice or CoreWeave; every failure came from
Parasail, which advertises everything and delivers neither channel.

**Bertan supplied the generation id that produced the mechanism.**
`gen-1787504499-mzoB1EaC4IeetQvcuI1x` carries a field the assistant's first bulk
lookup had not printed — `provider_responses`, the routing *chain*:

```
Parasail  status 429  latency 251ms   ← asked first, refused
Venice    status 200  latency 1084ms  ← served it
```

So MiniMax reaches a working provider **by falling back**. Every MiniMax success
on record is a call Parasail refused to serve; the failures are the runs where
Parasail was available. The panel's structured-output channel for MiniMax was
chosen on evidence generated by a rate limiter.

### `require_parameters` is exonerated, and worked exactly as specified

The standing suspicion from the previous session was that
`provider: {'require_parameters': True}`, which first reached the wire on
2026-08-25, had changed MiniMax's routing and broken it. It had not. Parasail
advertises `tools`, `response_format` **and** `structured_outputs`, so no filter
expressed in terms of advertised support has grounds to exclude it. Parasail was
also already serving MiniMax on 2026-08-23, in a run that carried no such
constraint.

A weaker point survives and is worth keeping: `require_parameters` filters on
`response_format`, while the `json_schema` channel actually needs
`structured_outputs`. For MiniMax, DeepInfra advertises the first and not the
second — eligible today, and it would degrade silently if drawn.

## The pivot: LangSmith is enabled in exactly one place

**Bertan's observation, and it reframed the problem.** `src/main_dev.py:27-29`
sets three LangSmith environment variables inside `main()`. **No probe and not
`judge.py` does.** Every panel run, both stability samples and the
reasoning-channel probe ran untraced — which is why the morning's questions had
to be answered from a web console at all.

The assistant's initial response was to propose enabling it everywhere and
letting it carry prompts and outputs. **That proposal was withdrawn later in the
session**, after Bertan reported his own experiments with it were
unsatisfactory. The cause is undiagnosed — possibly the OpenRouter client,
possibly free-tier ingest limits — and the assistant's position is that the
diagnosis does not change the decision, because the workload is structurally
close to LangSmith's worst case: large payloads, one judge call producing a
nested tree of runs through `with_structured_output(include_raw=True)` +
`with_retry`, and an in-process network round trip on each.

What demoting it costs is small, and the reason is specific: **our prompts are
reproducible** — a pure function of case id, stage and template at a known
commit. The one irrecoverable artefact is the raw text of a *failed* call, and a
database can hold that directly.

## Three measurements that shaped the design

### The served provider does not reach the message

The assistant claimed twice, from reading `langchain_openrouter/chat_models.py:870`,
that `response_metadata["provider"]` was available for free. **Measured on the
real judge path, it is absent:**

```
response_metadata keys: ['cost', 'cost_details', 'created', 'finish_reason',
                         'id', 'logprobs', 'model_name', 'model_provider', 'object']
provider -> None
```

The raw HTTP response for the same model carries it — top-level
`provider: Morph`. `_create_chat_result` calls `response.model_dump(by_alias=True)`
on the SDK object; declared fields such as `system_fingerprint` survive, and
`provider` does not.

### The generation record takes eight to ten seconds to exist

**Measured** — three calls, polling `/api/v1/generation` every 100 ms from the
moment `ainvoke` returned:

```
9321 ms (24 attempts)   8044 ms (22 attempts)   9735 ms (27 attempts)
```

OpenRouter writes the record asynchronously. This is what makes the log
two-phase; it is a property of the provider, not a design preference. For scale,
the fastest panelist answers a real A2 prompt in about 7 seconds.

### A local row write is free; a remote one is not, and is unmeasured

**Measured** — 300 single-row commits, realistic 19-column row:

| mode | median | p95 | max |
|---|---|---|---|
| default journal, `synchronous=FULL` | 3.226 ms | 6.128 ms | 19.167 ms |
| WAL, `synchronous=NORMAL` | **0.012 ms** | 0.022 ms | 0.050 ms |

This number was taken while SQLite was still the proposal. **It no longer
describes the chosen storage** and is kept only as the shape of the argument —
the remote Postgres figure is unmeasured and is the first thing to measure once
a URL exists.

## What Bertan decided

- **The model call stays bare.** Evaluations measure model latency, so the timer
  brackets `ainvoke` alone and every write happens after it stops. Bertan raised
  this against the assistant's proposal to enrich inside the call.
- **An `llm_call()` wrapper** at the five stage call sites — invoke, record,
  return — rather than end-of-run reconciliation. His phrasing: insert the
  generation-id information immediately after the call or before the script
  exits, and complete the incomplete rows afterwards.
- **Remote PostgreSQL through SQLAlchemy**, not a local file. His two reasons,
  both accepted: a gitignored local database has no backup, and committing it to
  a public repository is not acceptable either — it would publish every prompt,
  gold answer and cost in a binary that churns every run.
- **The database URL is optional.** If configured, `llm_call()` writes; if not,
  it does not.
- **A separate LangSmith project** for eval runs, chosen before the withdrawal
  above; whether it survives tracing being opt-in is now open.
- **Reports keep carrying their own numbers**, so a committed eval report stays
  checkable without an account.

## Traps recorded rather than solved

Written up in full in the design document; the two with the sharpest edges:

**A synchronous insert inside an async stage would serialise the panel.** The
stages are `async` and probes run panelists concurrently; a blocking database
call in the event loop makes eight panelists take turns on the network, with no
error and no symptom beyond a run that feels slow.

**Retries produce generations nobody sees.** `build_judge_llm` attaches
`.with_retry(stop_after_attempt=3)`. A retried call produces more than one
generation at the provider, each billed, and the returned message carries only
the last id. **Every cost total this project has reported may be an
undercount**, and the log as currently designed would inherit the same blind
spot. Unverified — it needs checking against the callback layer.
