## The high-severity finding was `eval(` inside the word `Retrieval(`

`threat-runtime-obfuscation-steganography`, severity `high`, MITRE
`defense-evasion`, at `google/genai/tests/models/test_generate_content_tools.py:217`.
The rule is YARA and its condition has two branches:

```yara
(any of ($py_stego_decode, $py_lsb_reveal, $py_stegano) and $img_png and ($py_exec or $py_eval)) or
(any of ($js_*)                                        and $img_png and $js_eval)
```

The Python branch scores **zero** — the file contains no `stegano`,
`lsb.reveal(` or `steganography.decode(`. The JavaScript branch fires, and it is
degenerate: `$js_eval` is itself a member of `$js_*`, so the whole branch reduces
to **`"eval(" AND an image filename`**. Both hold: `$js_eval = "eval(" nocase` is
a bare literal with no word boundary and matches inside `types.Retrieval(`, while
`$img_png` matches `'…/google_homepage.png'` at line 46. `path_include` covers
`*.py`, so an unguarded JavaScript pattern is applied to Python source.

The asymmetry is the whole bug. The Python patterns are written correctly —
`$py_eval = /[^.\w]eval\s*\(/` requires a non-word, non-dot character before
`eval` and would **not** match `Retrieval(` or `.eval()`. The JS pattern has no
such guard.

GuardDog's own report prints the match as the literal string `eval(`, so this is
confirmed from its output and not only from reading the rule.

**The same defect appeared in a second package.** `pillow==12.3.0` blocks on the
identical rule at `PIL/Image.py:3776`, matching ` eval(` on
`def eval(image, *args)` — Pillow's documented per-pixel API. Verified the same
branch fired: zero steganography strings in `Image.py`, and `$img_png` matches
`.bmp"` at line 329. Two of the three baseline blockers are one upstream defect.

## The cache could not have answered the question, and that is now fixed

Schema 4 dropped `findings` on 2026-08-11 because it was roughly twice the size
of `risks` and *"nothing reads it now that the verdict comes from `risks`"*. That
reasoning was sound and the conclusion was wrong within twenty-four hours: a
human adjudicating a waiver reads it. From a cache entry alone the google-genai
finding is a high-severity steganography detection at a named line, and there is
no way to discover that the matched text is `eval(`.

**`reports/` now sits beside the cache**, one file per key, named after the same
key. GuardDog's report in full plus one namespaced `_guarddog_cached` provenance
block. Written only for completed scans; replaced by rename; **no lock** — unlike
`cache.json` it is one file per key rather than a shared document, and two
projects scanning the same package version write the same content.

Filenames are sanitised. `REQ_RE` pins a package name to
`[A-Za-z0-9][A-Za-z0-9._-]*` but accepts any non-space, non-`;` run as the
*version*, which admits `/` and `..`. The requirements file is generated by
`uv export`, but a wrapper that writes files named after whatever it parsed
should not depend on that. Sanitising is many-to-one, so a rewritten key gets a
short digest appended — otherwise two versions could share one report and the
evidence shown for one would be the evidence gathered for the other.

## `issues: 15` versus `findings_count: 9` is a counting artifact, not hidden findings

Raised as a possible gap in what had been reviewed. `analyzer.py:543` does

distinct YARA *string identifiers* that matched in that file, while `results`

`issues` is a matched-string tally. Across all 74 calibration reports
`findings_count` equals the `results` total exactly; `issues` exceeds it in 29.
Nothing was ever withheld.

findings.

## A review ledger, because the reports directory is machine-wide and mostly boring

Of the 74 calibration reports only 17 carry any finding and 4 block. Re-reading
the rest on every pass is the kind of friction that produces rubber-stamping, so
`guarddog-review` lists what is outstanding and records decisions.

**The ledger never affects a verdict**, and that is pinned by a test. Only
`accepted.json` waives; recording a review prints a reminder saying so. A record
of *having looked* and a decision to *stop blocking* are different claims, and a
bookkeeping file that could quietly clear a finding would be a second waiver
mechanism with none of the first one's ceremony.

A review is of a *report*, not of a package, so entries key on the full cache key
— the same code under a newer GuardDog can produce findings nobody has seen — and
store a digest of what was adjudicated: each risk's rule, severity and location
plus the text it matched. A re-scan producing different matches re-opens the
entry. A review of `eval(` does not carry over to a report matching `exec(`.

## Four waivers, and a correction to the pyyaml assessment

The 2026-08-11 devlog recorded pyyaml's finding as *"behaviourally true, not a
false positive"*, and this session relayed that before checking it. The evidence
is more favourable, and the correction is the useful part.

**Which branch fired:** B — `__import__(` ∧ `getattr(module,` ∧
`base64.decodebytes`, all in `yaml/constructor.py`. Branch A (import + network +
exec) cannot fire; there is no network call in the file. The base64 at lines
299–308 and 505–511 is `construct_yaml_binary` implementing the `!!binary` tag,
**unrelated to the import machinery**. The correlation the rule rests on does not
hold here.

**What the flagged code does:** both `__import__` calls sit *inside `if unsafe:`
blocks*. `FullConstructor` calls `find_python_module`/`find_python_name` with
`unsafe=False`, so the import never runs and control falls to
`if name not in sys.modules: raise`. Only `UnsafeConstructor` (line 713)
overrides them to pass `unsafe=True`.

**Our exposure:** neither repository imports `yaml`. pyyaml is transitive via
`langchain-core`, whose only two call sites are `yaml.safe_load`
(`prompts/loading.py:131` and `:267`), and `SafeConstructor` does not bind the
`!!python/*` tags at all. The note in `accepted.json` records this and tells the
next reader to re-check it if we ever call `yaml.load`/`full_load`/`unsafe_load`
ourselves.

## `upgrade-safe` is all-or-nothing, and partial adoption rescues the keying question

Raised by Bertan. `uv lock --upgrade` upgrades everything and the `EXIT` trap
reverts `uv.lock` wholesale if either tier fires, so one blocked package reverts
forty that passed. The recipe's own advice on failure — `uv lock --upgrade-package
<other> …` — is inside-out: it asks you to name every package you *do* want.

Three things were settled about the fix:

- **Most of it must not be a skill.** Which packages are adopted has to produce
  the same answer in CI and a year from now. A skill fits the part that is
  genuinely judgement — reading a report and drafting the waiver.
- **Partial is not subtraction.** Excluding a blocked package means re-resolving,
  and the result is a *different lock* that must be gated in full, including the
  held-back packages at their old versions. Otherwise a tier-2 false positive can
  pin you to a version carrying a tier-1 advisory — trading a heuristic for a
  real one, quietly.
- **It resolves the undecided keying question.** `(name, version)` keying was
  under pressure because a strict key re-blocked *the whole upgrade* on an
  already-reviewed finding. With partial adoption the friction becomes local —
  one package held back instead of forty — so the strict key, which is the
  correct semantics, becomes affordable. **Option 1, "leave it", is now
  defensible rather than merely tolerable.**

A gap was identified and not closed: the candidate set does not survive the
revert. `mv -f uv.lock.preupgrade uv.lock` overwrites it, so the resolution a
reviewer is meant to review is gone. The reports survive, being written
per-package as scans complete, but nothing records *which versions were
proposed*.

## Tier 1 is a show-stopper by construction

There is no suppression path for OSV anywhere in the repo: `accepted.json` waives
GuardDog rules only. That is the right shape, because the two tiers make
different claims — a GuardDog finding is an inference about intent from a pattern
and is refutable by reading the code, while an OSV finding is a published record
of a known defect. `waiver-review` should never grow a tier-1 branch.

Two consequences that "show-stopper" obscures: a tier-1 failure exits before
GuardDog runs, so there are no tier-2 findings to review that round; and
reverting the upgrade returns you to a lock that may carry the same advisory.
`make audit` on the committed lock is what says where you actually stand.
